What Is Data?

Understanding the difference between structured, unstructured, and messy data — and why it matters.

📊 Structured vs Unstructured Data

Not all data is the same. The most important distinction for your work is this:

// Real World Analogy

A spreadsheet is like a filing cabinet where someone has shoved everything in the same drawer with no folders. A structured database is like a filing cabinet where every document is in the right folder, labelled, dated and cross-referenced. Both hold the same information. Only one is actually useful.

⚠️ What Bad Data Actually Looks Like

Most businesses you'll work with have data that looks something like this:

Three rows are the same person. Phone numbers are in four different formats. Notes contain orders, invoices, and relationship info all mixed together. A machine — or AI — cannot work with this.

🔍 Why This Matters for AI

Every business is trying to add AI tools right now. The problem is: AI needs clean, structured data to function properly. When you feed it the table above, it can't help you find all VIP customers, or generate a real invoice report, or detect lapsed clients. The mess defeats the intelligence. Cleaning data is the necessary first step — and that's the service you're building toward offering.

02

Databases

What databases are, how relational data works, and what SQL does — without writing any code.

🗂️ What Is a Database?

A database is a system for storing, organising, and retrieving data reliably. Unlike a spreadsheet, it's designed to handle thousands (or millions) of records, multiple users at once, and complex relationships between different types of information.

// The Hotel Analogy

Imagine a hotel. It has Guests (with names, contact details, preferences), Rooms (with numbers, types, prices), Bookings (connecting a guest to a room on specific dates), and Invoices (connecting a booking to a payment). Each of these is a separate table. They're connected by shared identifiers. You can instantly ask: "Show me all bookings for suite rooms by guests who've stayed more than three times." A spreadsheet cannot do this. A relational database does it instantly.

🔗 What "Relational" Means

A relational database stores data in multiple tables that are connected to each other. Each table has rows (records) and columns (fields). Tables connect via shared IDs.


customers table
orders table
id: 1
name: Jon Smith
email: jon@gmail.com
id: 101
customer_id: 1 ←
amount: £450
date: 2024-04-14

The customer_id: 1 in the orders table points to id: 1 in the customers table. That link is the relationship. Now you can ask: "Show all orders from Jon Smith" — without copying his name into the orders table 50 times.

🗣️ What Is SQL?

SQL (Structured Query Language) is the language used to talk to databases. You don't need to write it yourself to do this work — but reading it helps. Here's what it looks like in plain English:

-- "Show me all customers who haven't ordered in 6 months" SELECT name, email FROM customers WHERE last_order_date < '2024-01-01' ORDER BY last_order_date; -- "How much has each customer spent in total?" SELECT customer_id, SUM(amount) AS total_spent FROM orders GROUP BY customer_id;

Even without writing this yourself, you can see that SQL reads almost like English. You can describe these queries to a developer (or an AI) and they'll write the code. Your job is to know what questions to ask.

📝 Key Terms to Know

  • Table — like a spreadsheet tab, holds one type of record (customers, orders, etc.)
  • Row / Record — one single entry in a table (one customer, one order)
  • Column / Field — one piece of information (name, email, date)
  • Primary Key — a unique ID for each row, so nothing gets confused
  • Foreign Key — a column that links to another table's primary key
  • Schema — the overall design/structure of your tables and how they connect
  • Query — a question you ask the database (using SQL)
  • Index — makes searches faster, like an index in a book

Design on Paper

Draw lines between boxes where the records are related. Write 4–5 column names in each box. You've just designed a basic database schema — no code needed.

Supabase & Postgres

What these tools are, how they relate, and why businesses use them.

⚙️ Postgres — The Engine

PostgreSQL (called "Postgres") is one of the world's most trusted databases. It's open-source, free, and used by companies ranging from small startups to major banks. It's been around since 1996 and is extremely reliable.


Think of Postgres as the engine inside a car. It's what actually stores, organises, and retrieves your data. Powerful — but it doesn't come with a dashboard, seats, or steering wheel by default.

🚀 Supabase — The Platform

Supabase is a platform built on top of Postgres. It adds the dashboard, seats, and steering wheel. It gives developers everything they need to build an app quickly:

  • A hosted Postgres database (no server setup)
  • Built-in user login and authentication
  • Auto-generated APIs when you create tables
  • Real-time features (live dashboards, notifications)
  • File storage (photos, PDFs, documents)
  • A visual table editor (looks a bit like Airtable)
// Client-Friendly Explanation

"Supabase is the platform. Postgres is the engine underneath. Together they give you a proper, reliable database system that's searchable, scalable, and AI-ready — without having to build everything from scratch or pay enterprise prices."

Data Migration

What migration actually involves — from discovery to go-live — as a structured five-phase process.

📌 What "Migration" Actually Means

Data migration is the process of moving data from one system to another — usually from something messy and fragmented (spreadsheets, old CRMs, Access databases) into something structured and modern (Postgres, Supabase, a proper database). It's not just copying data. It's cleaning, restructuring, validating, and verifying it along the way.

📐 Phase 1 — Discovery & Audit

Before touching any data, you need to understand what exists. This is your most natural skill — it's essentially a process audit applied to data.

  • Where does data currently live? (spreadsheets, emails, WhatsApp, paper?)
  • Who owns and maintains it?
  • What decisions does the business make using this data?
  • What reports do they currently run (or wish they could run)?
  • What are the biggest pain points with data right now?
Your advantage: Business process consultants are trained to ask exactly these questions. You already know how to run this phase.

🗺️ Phase 2 — Schema Design

Based on discovery, you design the new structure. What tables do you need? What columns? How do they connect? This is the architectural phase — no data moves yet.

  • Define the main entities (customers, properties, jobs, invoices...)
  • List the fields each entity needs
  • Define the relationships between tables
  • Decide on data types (text, number, date, yes/no)
  • Think about what reports you'll need to run

🧹 Phase 3 — Data Cleaning

This is often the most time-consuming phase. Before data can move, it must be cleaned:

  • Standardise phone numbers (all to one format)
  • Standardise dates (all to YYYY-MM-DD)
  • Identify and merge duplicate records
  • Fill or flag missing critical fields
  • Split multi-value cells into proper separate records
  • Remove test data, junk rows, blank entries
// Before cleaning — phone number column: 07888 123456 +44 7888 123456 7888123456 07888-123-456 // After cleaning — all standardised: +447888123456 +447888123456 +447888123456 +447888123456

📦 Phase 4 — Import & Validate

The cleaned data is imported into the new database. Then it's validated — meaning you check that everything arrived correctly:

  • Do the record counts match?
  • Are all relationships intact?
  • Can you run the key queries the business needs?
  • Is anything missing or corrupted?
  • Test with real business scenarios ("find all lapsed customers")

✅ Phase 5 — Handover & Documentation

The migration is only complete when the client can actually use the system:

  • Simple documentation of the schema (what each table and column means)
  • Training the client or their team on retrieval and reporting
  • Setting up regular backup and maintenance processes
  • Archiving the original messy files (don't delete — just retire them)
  • Defining who maintains the data going forward
// Exercise 4.1 — Map a Migration

Think Through a Real Client

Think of a business you know personally or have worked with. Walk through all five phases in your head for them:

  • What would you find in Phase 1?
  • What tables would you design in Phase 2?
  • What cleaning problems would you expect in Phase 3?
  • What validation queries would matter in Phase 4?
  • Who would need training in Phase 5?

Write it out on paper. This is the skill at the core of what you're building.

Practice Exercises

Hands-on exercises to build the core migration muscle — no coding required.

// Exercise A — Beginner

The Chaos Customer Spreadsheet

Create a deliberately messy spreadsheet with 20–30 rows of fake customer data. Include: duplicate names in different formats, phone numbers in 4 different styles, missing emails, notes crammed with multiple types of information, inconsistent date formats, and blank rows.

Then: Design a clean 3-table structure (Customers, Orders, Notes). List what cleaning steps you'd need. Rewrite 5 rows into the clean format on paper.

Tools needed: Just Excel or Google Sheets.

// Exercise B — Intermediate

The Property Management Company

Imagine a property management firm tracking landlords, properties, tenants, maintenance jobs and invoices across WhatsApp, spreadsheets and PDFs.

Design: A full schema with at least 5 connected tables. For each table, write the column names. Draw the connections between tables. Then write 3 questions the business would want to ask ("Show all properties with outstanding maintenance jobs over 30 days old").

Tools needed: Paper and pen, or draw.io (free).

// Exercise C — Applied

The Supabase Table Editor

Go to supabase.com and create a free account. Create a new project. In the Table Editor (it looks like a spreadsheet), create a Customers table with columns: id, name, email, phone, created_at.

Then: Add 5 fake rows manually. Go to the SQL Editor and type: SELECT * FROM customers; — and see your data come back. You've just run your first database query.

Tools needed: Free Supabase account (no credit card).
